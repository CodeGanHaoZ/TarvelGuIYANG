# 技术与 Mock 边界

## 数据模型

详细样例位于 `lib/itinerary-fixtures.ts`；`TripDay.guide` 保存当天摘要、用餐、住宿和准备，`TripItem.plan` 保存可修改的最早开始时间与游玩说明。`TripItem.transport` 以 `fromId + mode` 绑定相邻路段，调序后旧选择不适用于新前驱。可选字段保持旧 v1 数据可恢复，恢复时验证结构；不自动替换用户已有空白日或非空日。

`lib/transport.ts` 为纯估算/链接模块，不发起网络请求。`metrics` 与 `timeline` 共用 `resolveTransport`；地图摘要和导出也使用同一计算。跨城日由 `previousDayConnection` 显式传入上日尾站，避免“瞬移”。`TransportPlanner` 提供模式筛选、排序、逐段说明、官方资料、高德与12306外链；未知公交禁用应用，估算不记入实际账本。见 `TRANSPORT_SOURCES.md`。

`AppData → trips[] → Trip.days[] → TripDay.items[]`。TripItem 只引用稳定 placeId，顺序直接取数组次序。地点统一放在 `places` 中，通过 category 区分景点、餐厅、体验等。

- Trip：目的地、日期、同行人、预算、偏好、节奏、笔记。
- TripDay / TripItem：日期、地点顺序、可编辑停留时长。
- Place：近似坐标、类型、样例营业时间、价格、评分因素、文化礼仪、数据提示。
- Expense：所属行程、付款人、费用；内部结算用整数分。
- SharedTrip：发布时的行程快照、发布说明、收藏与申请状态；复制时重建 ID，避免修改原作品。
- AppData：格式版本、当前旅行、收藏、费用、发现、外观偏好、离线资源状态。

新增 `AppData.savedPostIds` 保存本机规划素材，旧版 v1 缺失此字段时迁移为空列表，不重置已有行程。`Trip.sourcePostIds` 保留内容来源；通过独立内容页与“概览”回看。收藏删除不修改生成后的行程，复制行程也保留源引用。

`/inspiration/[id]` 从白名单 fixture 渲染完整内容页，不存在的 ID 返回 404。每页 metadata 使用对应标题、摘要和封面，不复用品牌 OG 图片。规划动作通过 `?plan=已知ID` 回到首页草稿，消费后移除该参数，任意未知 ID 不触发规划。

`score(place, scenario, preferences)` 提供品类推荐基础：品类专属八项出行权重与地点文旅特征组合，并执行闭园/天气上限约束。行程中的 `goScore` 在此基础上加入同行类型、实际到达耗时、停留与开放冲突，主视图只显示天气、人流、适合你、交通、时间五项。所有值均为 Mock；文化评分描述样例体验，不对文化群体作价值排名。

## 分层

`lib/day-plan.ts` 为所有新旧行程派生每日计划，不向原始景点列表插入虚构餐馆或酒店。按当天出发时间、模拟开放、用户最早开始约束、交通选择和停留时长，依次生成酒店、三餐、休息、交通和游览事件；每站给出三段活动。长游览中的午餐单列且延长时间，餐饮地点抵扣对应配套餐次。时间轴、今日概览、交通面板与导出攻略消费同一份 `DayPlan`。更改顺序、删除、替换、延时和添加后重新派生。

`Trip.travelerProfile` 保存普通、亲子、长者、儿童四类同行设置；`TripDay.settings` 保存开始时间、场景、住宿坐标、配套餐饮、房费与逐段交通方式。所有字段可选，旧数据不需重建。酒店只作示例起终点，名称不会自动地理编码。跨城次日从上日酒店（未开启酒店时从尾站）接续；未包含机场/车站往返、真实景区接驳和未列费用。交通仍是 Mock，地图按钮仅带入端点进行外部查询，不回填结果。

人均预算由景点、配套餐饮、交通分摊、住宿分摊组成。房间按两人一间向上取整，末日不计住宿。强度按模拟步行距离、游览/交通时长和户外玩法判定；同行类型改变步行估时与负荷阈值，不提供医疗或安全判断。闭园、超出开放、过晚用餐和高强度会降级推荐并提示，不会自动删改用户景点。

首页 `InspirationPlanner` 管理临时多轮对话、附件预览、取消与结果确认。`lib/planning-input.ts` 为独立纯函数，处理已知链接、文字/OCR 实体匹配、去重、删除指令、玩法澄清及简单出行参数；所有输入只作为数据，不执行其中指令或访问任意 URL。它不复用旧 `parseGuide` 的域名通用样例。

`lib/planning-ocr.ts` 按需加载 Tesseract.js，worker、WASM 与中英文模型均同源部署，图片只在浏览器内处理，支持取消/超时/类型/大小与分辨率限制。图片与原始对话不持久化；确认后经 `PlanningContext` 将来源摘要和参数带入原有 `TripWizard`。未知链接、OCR 失败或无可识别地点不会伪造路线。它不是多模态 LLM，也不识别无文字风景照片的地标。

```text
React 页面与 shadcn 交互原语
          ↓
lib/travel.ts：类型、fixture、纯函数规则、异步 Mock 解析
          ↓
localStorage：本机状态         Service Worker：按需静态资源缓存
```

`parseGuide` 的延时用于展示 loading。URL 不会发起网络抓取；自然语言仅作本地实体名称匹配，不能假装理解任意视频。生成按区域分组、偏好过滤、节奏限制每日数量，并以样例门票/体验价格检查预算。导入地点优先保留；未排入的地点会写入旅行笔记提示。

首页六类主题通过 `TripWizard.initialTheme` 打开创建流程。`tripCreationDefaults` 为山水、黔味、民族、古镇、户外、红色分别选择安顺、贵阳、黔东南、贵阳、荔波、遵义，按候选数量和停留/交通时间建议天数。主题入口清除先前导入地点与来源；普通创建、内容导入不继承上一次主题。所有初始值可编辑，生成结果没有任何地点时保留表单并提示调整，不保存空路线。成功后使用原有保存逻辑进入“我的行程”。

交通以 Haversine 距离乘演示道路系数，再按城市/城际平均速度换算。它不是实际导航模型。时间轴考虑开放起始、到达、停留、交通，并提示超过关闭时间。

动态重排为演示策略：雨/闭园替换一个户外点为同区室内点；无候选时移除并解释；拥堵改变顺序。真实气象风险、约束求解和同行通知均未接入。

## 推荐未来接口（仅设计，当前无这些 HTTP 端点）

| 接口                         | 用途             | 关键要求                                             |
| ---------------------------- | ---------------- | ---------------------------------------------------- |
| POST /api/guides/parse       | 授权来源内容解析 | 来源域白名单、授权、超时、配额、结构化实体、人工校验 |
| POST /api/trips/plan         | 规划候选路线     | 时间窗、交通矩阵、预算约束、可解释拒绝/降级          |
| PATCH /api/trips/:id         | 保存行程         | 登录、所有权校验、版本号、冲突处理                   |
| POST /api/trips/:id/optimize | 优化路线         | 保留已锁定节点、可靠路线矩阵、前后对比               |
| GET /api/places/:id/context  | 今日指数与事实   | 每个字段的来源、更新时间、实时/预测类型              |
| POST /api/trips/:id/replan   | 处理突发变化     | 用户确认后应用，不擅自取消预订                       |
| POST /api/discover           | 发布行程         | 默认脱敏、审核、举报、权限控制                       |
| POST /api/companions         | 发起结伴         | 鉴权、限流、反骚扰、接收方确认                       |
| POST /api/sync               | 同步离线修改     | 幂等 mutationId、乐观版本、冲突合并与重试            |

## 可靠性与隐私

没有 API Key、登录令牌或真实用户数据库。没有上传文档/照片、剪贴板读取、定位权限申请或支付。用户输入由 React 作为文本渲染；URL 不用于 iframe 或 HTML 注入。

设备本地数据是显式 Mock 状态，不是云端账号资产。共享电脑可能看到同一浏览器的行程；导出文件包含同行人名称与笔记，应自行检查再分享。生产阶段需数据最小化与完整隐私流程。

Service Worker 只缓存同源 GET 页面/静态资源，不上传。只在用户点击缓存后注册；离线无法保证新页面或未缓存模块可用。生产上线若加入鉴权，需重新设计页面缓存与退出清除策略，不能直接沿用 Demo 策略。

## 验证策略

`lib/themed-fixtures.ts` 保存六类热门内容、具体玩法、全文与品类原始值，仅通过 type import 依赖模型。`travel.ts` 聚合新旧内容，旧内容 ID 与存储版本保持不变；恢复时将旧主题名迁移为新的六类名称。TypeScript 直接导入扩展名用于保持原生 Node 规则测试与 Vite 构建一致。

分类单元为“地点 + 玩法”。可选 `locationId` 表示同一地理场所，`id` 表示独立玩法。提取只按 `id` 去重；同 `locationId` 的不同玩法保留、提示且默认分日。建议天数与日程使用同一分组函数，按区域、8 小时模拟时长和每日数量约束，无法排入的地点写入备注。此时长模型不是导航或体力适宜性保证。

原生 Node test 覆盖评分、日期边界、偏好过滤、导入去重、预算、路线优化、时间冲突、精确分摊、异常重排、本地数据恢复与解析降级。TypeScript 检查组件与数据模型，oxlint 检查代码及基础可访问性，Vinext/Vite 产出 Worker 构建。

浏览器交互、视觉和真正断网重载测试尚未执行，不能以纯函数测试代替。接入真实地图、支付或多人状态后必须增加端到端与安全测试。
